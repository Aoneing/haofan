## 一、现状：代码已就绪，只差三个环境变量

`cloudfunctions/dishImage/index.js` 已经写好了完整三层逻辑，**不需要改代码就能启用**，缺的只是配置：

| 环境变量 | 含义 | 示例 |
|----------|------|------|
| `IMAGE_API_URL` | OpenAI 兼容的文生图接口地址 | `https://open.bigmodel.cn/api/paas/v4/images/generations` |
| `IMAGE_API_KEY` | 对应 Bearer Token | `sk-xxxx` |
| `IMAGE_API_MODEL` | 必填，智谱填 **`glm-image`** | `glm-image` |
| `IMAGE_API_SIZE` | 可选，默认 `1024x1024` —— 向接口请求的尺寸，兼容面最广；换服务商若报尺寸错再改 | `1024x1024` |
| `IMAGE_TARGET_SIZE` | 可选，默认 `640` —— 落库前缩到的长边像素 | `640` |
| `IMAGE_TARGET_QUALITY` | 可选，默认 `70` —— JPEG 质量（40–95） | `70` |

云函数只认这三样，请求体固定为 `{ model, prompt, n: 1, size: '1024x1024' }`，响应支持 `b64_json` 或 `url` 两种返回（给外链时会中转下载再入云存储，避免外链过期）。

未配置时前端会收到 `NOT_CONFIGURED` 并弹「还没配置生图服务」提示——这条已在阶段三用例 E-5 验证通过。

## 二、硬约束：不能用 OpenAI 官方接口

**微信云函数运行在境内腾讯云节点，`api.openai.com` 不可达。**所以：

- ❌ `https://api.openai.com/v1/images/generations` —— 连不上，别浪费时间
- ✅ 必须选**境内可直连**且**提供 OpenAI 兼容 `/images/generations`** 的服务

（兼容模式很关键：云函数只发了 OpenAI 格式的请求体，不支持各家自定义 SDK 协议。）

### 推荐：智谱 BigModel · `glm-image`

> ⚠️ **更正（2026-09-23 实测）**：国内站 open.bigmodel.cn 的模型列表里已经**没有 `cogview-4`** 了。
> 官方文档 `docs.bigmodel.cn/cn/guide/models/image-generation/glm-image` 当前主推的图像模型是 **`glm-image`**（¥0.1/张）。
> 老 CogView-4 只在国际站以 `cogview-4-250304` 这个带日期后缀的 ID 存在，国内站调不到。
> **以控制台「模型广场」里能看到的实际 ID 为准。**

理由三条：

1. **中文菜名理解最好**——我们的 prompt 是「家常辅食/菜品的手机美食摄影照片：「莲藕消积米糊」」这种含具体食材名的描述，中文模型胜出明显。
2. **便宜**——¥0.1/张，手动触发模式下一周也就几张到十几张，**月成本几块钱**。
3. **接口与我们的云函数天然契合**：
   - 端点 `https://open.bigmodel.cn/api/paas/v4/images/generations`
   - 返回 `data[0].url`（临时链接，30 天过期）——云函数会**中转下载再入云存储**，正好规避过期问题
   - `size` 支持 1024×1024～2048×2048（需被 32 整除），我们默认发的 `1024x1024` 合法

备选：如果 `glm-image` 出图风格不满意（偏插画不够写实），换**硅基流动的 FLUX.1-dev**（`https://api.siliconflow.cn/v1/images/generations`），写实摄影更稳，换两个环境变量就行。

### 顺带的好消息：内容安全有了低成本解法

智谱的响应里带 `content_filter` 字段：

```json
{ "created": 1760335349, "data": [{ "url": "..." }],
  "content_filter": [{ "role": "assistant", "level": 1 }] }
```

`level` 范围 0–3，**0 最严重、3 最轻**。这等于服务端已经帮我们做了安全判定，只要把它落库、对低分级图做打标或拒绝展示，P-1 的成本就极低（见第七节）。

## 四、接入步骤（全程约 15 分钟）

### 1. 注册并拿 Key

- 打开 <https://open.bigmodel.cn> → 注册登录 → 控制台「API Keys」→ 复制 Key（`sk-` 开头）
- 新用户有免费额度，**先不用充值**，跑通了再说

### 2. 填环境变量

1. 微信开发者工具 → 「云开发」打开控制台
2. 左侧「**云函数**」→ 点 `dishImage`
3. 「**配置**」页签 → 「环境变量」→ 添加：

   ```
   IMAGE_API_URL   = https://open.bigmodel.cn/api/paas/v4/images/generations
   IMAGE_API_KEY   = <你复制的 Key>
   IMAGE_API_MODEL = glm-image
   ```

   同时把**执行超时改成 20–60 秒**（默认 3 秒，生图必然超时）、**内存改成 512MB**（解 1024 图用）。

   > ⚠️ 内存/超时不是越大越好：若该套餐不支持所选规格，容器会拉不起来，表现为调用直接报 `-3 Upstream error`。配好后务必用「云端测试」验证能调通。

4. 保存

### 3. 重新部署（别漏，改了环境变量必须重新部署才生效）

开发者工具左侧文件树 → `cloudfunctions/dishImage` 右键 → **「上传并部署：云端安装依赖」**

> ⚠️ 压缩依赖经过瘦身（见下），首次部署会多花 1–2 分钟装依赖。
> 若依赖安装失败，云函数会在压缩那一步自动降级为「原样保存」并打 warn 日志，AI 配图功能不会挂，只是图会偏大。

#### 依赖瘦身：25.8MB / 60 包 → 5.4MB / 31 包

压缩只需要「读 PNG/JPEG → 缩放 → 编码 JPEG」，所以不引完整 `jimp`，改为按需装配 4 个子包：

```json
"@jimp/core": "^0.22.12", "@jimp/jpeg": "^0.22.12",
"@jimp/png": "^0.22.12", "@jimp/plugin-resize": "^0.22.12"
```

```js
// 组装入口是 @jimp/custom（@jimp/core 导出的是 Jimp 类本身，不能当 configure 用）
const Jimp = require('@jimp/custom').default({ types: [jpeg, png], plugins: [resize] });
// @jimp/plugin-resize 只有 resize()，没有 scaleToFit()，长边缩放在代码里算
```

对比：完整 `jimp` 25.8MB / 60 个包 → 瘦身版 **5.4MB / 31 个包**，云端 `npm install` 更快更稳。

### 4. 前端试跑

- 开发者工具「预览」扫码 → 今日页 → 展开某餐 → 点「菜品详情 ›」→ 点「生成配图」
- 首次生成可能要等 20–60 秒（生图 + 上传云存储）

## 七·补、AI 配图异步化设计（P-5 落地）

### 为什么云函数不能改成「返回后后台继续跑」

直觉方案是 `generate` 立即返回 `{pending:true}`，让生图任务在后台继续。但**微信云开发云函数是 `exports.main = async (event, context)` 形态**，async handler 一旦 return，平台即认为本次调用结束并冻结容器，尚未完成的异步任务会被挂起、不能保证执行完。腾讯云 SCF 里能让返回后继续跑的开关 `context.callbackWaitsForEmptyEventLoop` 只对 callback 形态的 handler 有效，微信云函数不支持。

所以结论是：**云函数侧必须保持「同步跑完再返回」，异步化只能做在前端。**

> 顺带纠正一个常见误解：调用方超时断开 **≠** 生成失败。已实测（DB 记录时间早于报错时间 7 秒）——云函数在调用方断开后仍会跑完并落库。

### 实现要点

**前端** `miniprogram/pages/dish/dish.js`

1. 点「生成 AI 配图」后 **2 秒内**给出反馈：按钮变「生成中…」+ 文案「AI 生成中，通常需要 30～60 秒」
2. 发起 `generate` 调用但**不拿它的返回值当结论**（返回值可能永远不来，也可能晚于轮询结果到达）
3. 立即开始轮询 `resolve`：**前 90 秒每 3 秒一次，之后每 10 秒一次，总上限 4 分钟**（生图实测 30 秒～2 分钟+，波动大，120 秒窗口实测不够用）：
   - 拿到 `fileID` → 写内存缓存 + 更新 UI + 提示「配图已更新」，停止
   - 超过 4 分钟 → 弹窗说明「就算这里超时，云端也常会继续跑完，退出本页再进来即可看到」，**不报错**
4. `generate` 调用被掐断（catch）属于**预期情况**，只记 warn、继续轮询，不弹失败提示
5. `onUnload` / `onHide` 必须停轮询，否则后台会继续发请求并 `setData`
6. `_applied` 单次标记：避免「generate 返回」与「轮询命中」对同一张图弹两次提示

**云函数** `cloudfunctions/dishImage/index.js`

| 保护 | 说明 |
|------|------|
| **成品复用** | 已存在的图直接返回 `cached: true`，不调接口 |
| **幂等窗口** | 3 分钟内重复请求同一 key 直接返回 `pending: true`，不重复调用生图接口 —— **重复调用＝重复扣费** |
| **失败冷却** | 连续失败 3 次后暂停 2 分钟，避免接口异常时反复烧钱 |
| **状态落库** | `status: pending / ready / failed` + `pendingAt / failedAt / failCount / lastError`，排查时看这一条记录就知道卡在哪 |
| **失败不丢旧图** | 失败写回时保留原 `fileID` |
| **统计口径修正** | `stats` 改为只统计 `fileID` 存在的记录，pending/failed 占位不再污染「配图库 N 张」 |
| **安全判定留存** | 智谱返回的 `content_filter` 落库，为 P-1 内容安全留数据 |

### 已验证（临时冒烟，6/6 通过）

用可控时钟 + 桩化的 `wx.cloud` 实测了轮询状态机：

| 用例 | 结果 |
|------|------|
| A `generate` 调用被超时掐断 | ✅ 轮询第 2 次拿到图，成功提示恰好 1 次 |
| B 一直没生成出来 | ✅ 约 2 分钟后给明确文案并停轮询，`generating` 复位 |
| C `generate` 悬挂永不返回 | ✅ 仍能靠轮询拿到图，不卡死 |
| D 图已在库（走 cached） | ✅ 只弹一次提示 |
| E 未配置生图服务 | ✅ 立即弹窗且停止轮询 |
| F 重复点击 | ✅ 第二次被挡住，不会再发起调用 |

### 部署后的验证动作

1. 重新部署 `dishImage`（右键 → 上传并部署：云端安装依赖），**部署完等 2–3 分钟**
2. 小程序里挑一道**没有配图的菜**点「生成 AI 配图」
3. 期望：按钮立刻变「生成中…」并显示等待文案；30～90 秒后自动出现图 + 「配图已更新」
4. 若超过 4 分钟才出图：说明单次生图 > 240 秒，需要同时提高**云函数执行超时**并调大 `POLL_MAX_MS`。注意「云端测试」入口跑 diag / generate 都会因调用方等待上限报 -3，**这不代表失败**，真实耗时以 DB 里 `generatedAt - 点击时间` 为准
5. 若始终不出图：看 `dishImages` 记录的 `status` 与 `lastError`（diag 也会因 -3 看不到返回，日志才是证据）

## 七·补2、图片送不到前端：云存储权限被免费套餐锁死（2026-09-26 定位并修复）

### 现象

- 数据库 `dishImages` 里记录完整（`status=ready`、`fileID` 有值、`bytes` 正常），**但小程序里图区空白**
- 点「点击查看大图」**一直转圈**，永远出不来
- 按钮显示的是「换一张配图」——说明前端**已拿到 fileID**，链路是通的

### 根因

云开发控制台 → **存储 → 权限设置**，当前是 **「仅创建者可读写」**；点修改弹出：

> 权限变更：当前套餐处于免费期，无法执行此操作，请升级至付费版使用

而配图是**云函数上传**的，客户端不是「创建者」。官方文档（云开发·存储·组件支持）写得很明确：

> fileID 可以直接填入 `image` 的 src / `previewImage` 的 urls；**但直接访问遵循对象存储的权限配置**，如遇权限拒绝请先检查权限配置。

⇒ `cloud://` 当 src 用会被拒 → 空白 + 预览无限转圈。**这与「生图失败」完全是两回事**：查库有记录 ⇒ 生成没问题，是「读」被拒。

### 解法：云函数换成 https 临时链接（免费，不必升级套餐）

云函数是**管理员身份**，能换出带签名的链接给客户端用（客户端自己调会被权限拒绝）：

```
resolve  → { map: { 菜名: "https://…" }, files: { 菜名: "cloud://…" }, missing: [...] }
generate → { ok, fileID, url: "https://…" }
```

云函数实现要点（`cloudfunctions/dishImage/index.js`）：

| 点 | 说明 |
|---|---|
| 新增 `toTempUrls(fileIDs)` | 批量调 `cloud.getTempFileURL`；**接口一次最多 50 个，超出必须分批** |
| `resolve.map` 改出 https | 原始 `fileID` 另放 `files` 备排查；换链接失败时**不把 `cloud://` 兜底返回**（否则前端又空白），只打 warn |
| `generate` 出参加 `url` | 生成成功当场换好链接，前端不必再跑一次 resolve |
| 换链接失败不抛错 | 个别文件换不到不该让整批查询失败 |

前端要点：

| 点 | 说明 |
|---|---|
| `utils/imageStore.js` 缓存 `{url, at}` | **缓存的是链接，不是 fileID**；私有读临时链接约 2 小时有效，按 **30 分钟**保守过期 |
| 判「要不要重取」看 TTL | 只看「缓存里有没有」会把过期链接一直用下去，图片迟早变白 |
| `reload(keys)` | 强制重取（无视 TTL），用于加载失败后的自愈 |
| `dish-thumb` 加 `binderror` | 加载失败就 `reload` 一次换新鲜链接；**只重试一次**，避免真失败时打成请求风暴 |
| 组件新增 `imgkey` 属性 | 自愈需要菜名才能重取；`day-card` 已透传 `item.key` |
| 各页 `onShow` 仍走 `hydrate` | today / week / day / import / dish 全都复用同一套缓存，TTL 逻辑自动生效 |

### 已验证（临时冒烟）

- **云函数 13/13**：`resolve` 只出 https（不出 cloud://）、60 张按 50+10 分批、换链接失败时 map 为空但不抛错且 `files` 仍可排查、`force` 绕过成品缓存、pending 窗口对 `force` 仍生效
- **前端 11/11**：首取 / TTL 内不重取 / TTL 过期重取 / `reload` 强制重取 / 并发不丢 key / resolve 失败不崩 / `set` 后计时重置

### 顺带修掉的 bug：「换一张配图」永远换不了

加了幂等保护后，`if (prev.fileID) return cached` 会让按钮**永远返回同一张图**，前端还照样弹「配图已更新」。现增加 `force` 参数：前端在已有图时（按钮文案是「换一张配图」）传 `force: true`；**pending 窗口对 force 依然生效**，连点两下不会重复扣费。

## 八、风险关注点

1. **Key 安全**：Key 放在云函数环境变量里是正确的（不进代码库、不进小程序包），但**别提交到 GitHub**——`cloudfunctions/dishImage/index.js` 里不要硬编码任何 Key。
2. **出网依赖**：配图功能依赖第三方接口可用性，接口挂了只影响「生成」，不影响已有配图展示（`resolve` 走数据库）——这个降级设计是对的。
3. **额度告警**：建议在服务商后台设置余额告警，避免免费额度用完后静默失败（表现为一直弹「还没配置生图服务」以外的错误提示）。
4. **合规**：个人小程序涉及 AI 生成内容，正式发布时审核可能问及；保留手动触发 + 生成记录可追溯是当前最稳的姿态。
5. **免费套餐锁死云存储权限**（新发现，2026-09-26）：本环境存储权限固定为「仅创建者可读写」，控制台改权限要求升级付费版。所有**云函数上传**的文件都必须经 `getTempFileURL` 换链接后才能给客户端读——新增任何「云函数产图/产文件」的功能，都要照「七·补2」的方式出参，别直接把 `fileID` 交给前端。若日后升级付费套餐，可改权限为「所有用户可读」并去掉这一层转换（当前实现即使权限放开也能正常工作，只是多一次换链接）。

## 十、常见报错速查

| 现象 | 原因 | 处理 |
|------|------|------|
| 「生图接口返回 404」或提示模型不存在 | `IMAGE_API_MODEL` 填了 `cogview-4`，国内站已无此模型 | 改成 `glm-image` |
| 「生图接口请求超时」 | 云函数执行超时还是默认 3 秒 | 超时改 60 秒，内存改 512MB |
| 「生图接口返回 401」 | Key 填错/失效，最常见是漏了点号后那段或带了空格 | 重新复制，确认无空格无引号 |
| 「生图接口返回 429」+ 错误码 1113 | 智谱账户余额不足 | 去费用中心充值，¥5–10 够用很久 |
| 「还没配置生图服务」 | 环境变量没存上，或没重新部署 | 检查三条变量，重新「上传并部署：云端安装依赖」 |
| **图能生成、DB 里也有记录，但小程序图区空白、点大图一直转圈** | ⭐ **已定位**：云存储权限是「仅创建者可读写」（免费套餐锁死，控制台改不了），云函数上传的文件客户端读不到 | 已修：云函数统一换 https 临时链接返回（见「七·补2」）。**重新部署 dishImage + 重新编译小程序**即恢复 |
| 图能生成但显示不出来，且日志有异常 | 大概率是旧版本代码在跑（$LATEST 早于 09-19 13:56） | 重新部署 dishImage |
| **调用报 `-3 / [UPSTREAM] Upstream error`，但数据库里其实有记录** | ⭐ **已定位**：调用方等待上限被突破而断开，**云函数仍在后台跑完并落库**。官方 FAQ 原文：「超时客户端会直接断开连接并报错……不允许直接调用长耗时的云函数」 | 不是故障。前端已异步化（见「七·补」），超时会自动走轮询拿到图，无需人工处理 |
| 调用报 `-3`，且**数据库里没有记录、日志里也没有任何 `[dishImage]` 输出** | 容器确实没起来 | 走下方「ret=-3 二分定位」 |
| 日志里出现 `compress skipped` | 压缩依赖没装上或解图失败 | 功能不受影响（自动降级存原图），但要核对 `bytes`；确认部署时选的是「云端安装依赖」 |

### ret=-3 二分定位（已定位，此处保留为方法论）

**2026-09-26 实测结论**：`resolve`（秒回）成功、`generate`（约 30 秒）报 -3 —— 看着像"函数坏了"，实际是**长耗时函数被调用方超时断开**：`dishImages` 里留下了 `_id=番茄炒蛋` 的完整记录，`generatedAt = 22:29:27`，而报错时间是 `22:29:34`（**函数比报错早 7 秒就成功了**）。

**所以第一件事永远是先查库**，`dishImages` 里有没有那条记录？

- **有记录** ⇒ 函数成功，-3 来自调用方超时，属预期行为，**不是缺陷**（但要按 P-5 修用户体验）
- **没记录** ⇒ 才是真失败，再按下面的表二分：

| 步骤 | 操作 | 结论判读 |
|------|------|----------|
| T1 | 在同一个「云端测试」面板调**另一个**云函数（如 `menuQuery`，参数 `{}`） | 也报 -3 ⇒ **环境级问题**（欠费/停服/额度），与代码无关；正常返回 ⇒ dishImage 独有，继续 T2 |
| T2 | 调 `dishImage` 传 `{"action":"diag"}` | 看返回体 / 日志里最后一条 `[dishImage][diag]` 标记停在哪段，即可定位死点 |
| T3 | 看开发者工具**部署输出窗口**，`npm install` 那段有没有报错 | 有报错 ⇒ **依赖在云端没装上**（已做瘦身，重试一次） |
| T4 | 兜底：临时把 `package.json` 里的 4 个 `@jimp/*` 全删掉再部署 | 恢复 ⇒ 依赖问题实锤，改用零依赖方案（存原图，用 `IMAGE_API_SIZE` 向接口要小图） |
