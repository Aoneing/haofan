## 一、现状：代码已就绪，只差三个环境变量

`cloudfunctions/dishImage/index.js` 已经写好了完整三层逻辑，**不需要改代码就能启用**，缺的只是配置：

| 环境变量 | 含义 | 示例 |
|----------|------|------|
| `IMAGE_API_URL` | OpenAI 兼容的文生图接口地址 | `https://open.bigmodel.cn/api/paas/v4/images/generations` |
| `IMAGE_API_KEY` | 对应 Bearer Token | `sk-xxxx` |
| `IMAGE_API_MODEL` | 必填，智谱填 **`glm-image`** | `glm-image` |
| `IMAGE_API_SIZE` | 可选，默认 `1024x1024` —— 向接口请求的尺寸，兼容面最广；换服务商若报尺寸错再改 | `1024x1024` |
| `IMAGE_TARGET_SIZE` | 可选，默认 `640` —— 落库前缩到的长边像素 | `640` |
| `IMAGE_TARGET_QUALITY` | 可选，默认 `70` —— JPEG 质量（40–95） | `70` |

云函数只认这三样，请求体固定为 `{ model, prompt, n: 1, size: '1024x1024' }`，响应支持 `b64_json` 或 `url` 两种返回（给外链时会中转下载再入云存储，避免外链过期）。

未配置时前端会收到 `NOT_CONFIGURED` 并弹「还没配置生图服务」提示——这条已在阶段三用例 E-5 验证通过。

## 二、硬约束：不能用 OpenAI 官方接口

**微信云函数运行在境内腾讯云节点，`api.openai.com` 不可达。**所以：

- ❌ `https://api.openai.com/v1/images/generations` —— 连不上，别浪费时间
- ✅ 必须选**境内可直连**且**提供 OpenAI 兼容 `/images/generations`** 的服务

（兼容模式很关键：云函数只发了 OpenAI 格式的请求体，不支持各家自定义 SDK 协议。）

### 推荐：智谱 BigModel · `glm-image`

> ⚠️ **更正（2026-09-23 实测）**：国内站 open.bigmodel.cn 的模型列表里已经**没有 `cogview-4`** 了。
> 官方文档 `docs.bigmodel.cn/cn/guide/models/image-generation/glm-image` 当前主推的图像模型是 **`glm-image`**（¥0.1/张）。
> 老 CogView-4 只在国际站以 `cogview-4-250304` 这个带日期后缀的 ID 存在，国内站调不到。
> **以控制台「模型广场」里能看到的实际 ID 为准。**

理由三条：

1. **中文菜名理解最好**——我们的 prompt 是「家常辅食/菜品的手机美食摄影照片：「莲藕消积米糊」」这种含具体食材名的描述，中文模型胜出明显。
2. **便宜**——¥0.1/张，手动触发模式下一周也就几张到十几张，**月成本几块钱**。
3. **接口与我们的云函数天然契合**：
   - 端点 `https://open.bigmodel.cn/api/paas/v4/images/generations`
   - 返回 `data[0].url`（临时链接，30 天过期）——云函数会**中转下载再入云存储**，正好规避过期问题
   - `size` 支持 1024×1024～2048×2048（需被 32 整除），我们默认发的 `1024x1024` 合法

备选：如果 `glm-image` 出图风格不满意（偏插画不够写实），换**硅基流动的 FLUX.1-dev**（`https://api.siliconflow.cn/v1/images/generations`），写实摄影更稳，换两个环境变量就行。

### 顺带的好消息：内容安全有了低成本解法

智谱的响应里带 `content_filter` 字段：

```json
{ "created": 1760335349, "data": [{ "url": "..." }],
  "content_filter": [{ "role": "assistant", "level": 1 }] }
```

`level` 范围 0–3，**0 最严重、3 最轻**。这等于服务端已经帮我们做了安全判定，只要把它落库、对低分级图做打标或拒绝展示，P-1 的成本就极低（见第七节）。

## 四、接入步骤（全程约 15 分钟）

### 1. 注册并拿 Key

- 打开 <https://open.bigmodel.cn> → 注册登录 → 控制台「API Keys」→ 复制 Key（`sk-` 开头）
- 新用户有免费额度，**先不用充值**，跑通了再说

### 2. 填环境变量

1. 微信开发者工具 → 「云开发」打开控制台
2. 左侧「**云函数**」→ 点 `dishImage`
3. 「**配置**」页签 → 「环境变量」→ 添加：

   ```
   IMAGE_API_URL   = https://open.bigmodel.cn/api/paas/v4/images/generations
   IMAGE_API_KEY   = <你复制的 Key>
   IMAGE_API_MODEL = glm-image
   ```

   同时把**执行超时改成 20–60 秒**（默认 3 秒，生图必然超时）、**内存改成 512MB**（解 1024 图用）。

   > ⚠️ 内存/超时不是越大越好：若该套餐不支持所选规格，容器会拉不起来，表现为调用直接报 `-3 Upstream error`。配好后务必用「云端测试」验证能调通。

4. 保存

### 3. 重新部署（别漏，改了环境变量必须重新部署才生效）

开发者工具左侧文件树 → `cloudfunctions/dishImage` 右键 → **「上传并部署：云端安装依赖」**

> ⚠️ 压缩依赖经过瘦身（见下），首次部署会多花 1–2 分钟装依赖。
> 若依赖安装失败，云函数会在压缩那一步自动降级为「原样保存」并打 warn 日志，AI 配图功能不会挂，只是图会偏大。

#### 依赖瘦身：25.8MB / 60 包 → 5.4MB / 31 包

压缩只需要「读 PNG/JPEG → 缩放 → 编码 JPEG」，所以不引完整 `jimp`，改为按需装配 4 个子包：

```json
"@jimp/core": "^0.22.12", "@jimp/jpeg": "^0.22.12",
"@jimp/png": "^0.22.12", "@jimp/plugin-resize": "^0.22.12"
```

```js
// 组装入口是 @jimp/custom（@jimp/core 导出的是 Jimp 类本身，不能当 configure 用）
const Jimp = require('@jimp/custom').default({ types: [jpeg, png], plugins: [resize] });
// @jimp/plugin-resize 只有 resize()，没有 scaleToFit()，长边缩放在代码里算
```

对比：完整 `jimp` 25.8MB / 60 个包 → 瘦身版 **5.4MB / 31 个包**，云端 `npm install` 更快更稳。

### 4. 前端试跑

- 开发者工具「预览」扫码 → 今日页 → 展开某餐 → 点「菜品详情 ›」→ 点「生成配图」
- 首次生成可能要等 20–60 秒（生图 + 上传云存储）

## 五、成本测算（按设计文档「手动触发」模式）

| 项目 | 估算 |
|------|------|
| 触发频率 | 手动，一周 5–15 张（不会到 35 张全生成） |
| 月调用量 | 约 20–60 张 |
| 生图费用 | ¥0.02–0.10 / 张 → **月 ¥0.4–6** |
| 云存储 | 见下方 ⚠️ |

> ⚠️ **容量风险（实测后基本消除）**：设计文档规划 WebP / 长边 640px / 单图 40–80KB。首张真实落库数据 `bytes = 71,994`（70.3KB），**已落在规划区间内**。

## 七、本次发现的问题（接入前建议一并处理）

| 编号 | 问题 | 依据 | 建议 | 优先级 |
|------|------|------|------|--------|
| P-1 | **内容安全未做**：AI 生成图片直接入云存储并展示，个人小程序对 AI 生成内容有合规要求，设计方案第 07 节也提到「需要内容安全机制」 | 设计文档 07 节 vs `dishImage/index.js` | ✅ **有了低成本解法**：智谱响应自带 `content_filter.level`（0–3，0 最严重）。把它落库并对低分级图打标/拒绝展示即可，无需额外接安全检测服务。若后续开放自动批量生成，必须做这层拦截 | P1 |
| P-2 | **图片规格偏离设计**：硬编码 `size: '1024x1024'`、存 PNG，设计文档要求 WebP / 640px / 40–80KB | 设计文档 07 节「图片规格与容量」 | ✅ **已修并实测闭环**：落库前用 jimp 缩到长边 640 并重编码 JPEG q70。首张真实数据：`rawBytes 121,474 → bytes 71,994`（118.6KB → 70.3KB，省 41%），**落在设计要求的 40–80KB 区间内**。压缩没变小的极端图（纯色/简单图）自动保留原图。⚠️ 原估算「单图 1–2MB」是假设值，glm-image 实际输出约 119KB，所以收益是 41% 而非 20 倍 | P2 → 已修 |
| P-3 | **尺寸参数不通用**：各家对 size 的写法不同（如通义万相用 `1024*1024`），当前硬编码 OpenAI 写法 | 各家 API 文档 | 换服务商时若报错，先看是否是 size 格式问题 | P3 |
| P-4 | **`hitCount` 未实现**：设计文档要求图库命中后 `hitCount + 1` 用于统计「哪些菜最常吃」 | 设计文档 07 节一层 | 属二期候选，暂不阻塞 | P3 |
| P-5 | ⭐ **生图必须异步化**：生图约 30 秒，超过调用方等待上限，客户端会直接断开并报错；而云函数在后台仍跑完落库。结果：用户看到「失败/无响应」，其实图已经生成好了，下次进页面才出现。官方 FAQ 明确写「不允许直接调用长耗时的云函数」 | 2026-09-26 实测：DB 记录 `generatedAt 22:29:27`，报错时间 `22:29:34` | 方案：`generate` 立即返回 `{ok:true,pending:true}`（用 `context.callbackWaitsForEmptyEventLoop = false` + 不 await 后台任务），前端拿到 pending 后**轮询 `resolve`**（建议 3 秒一次、最多 90 秒），图出现即停。这样彻底不依赖客户端等待上限 | P1 |

## 八、风险关注点

1. **Key 安全**：Key 放在云函数环境变量里是正确的（不进代码库、不进小程序包），但**别提交到 GitHub**——`cloudfunctions/dishImage/index.js` 里不要硬编码任何 Key。
2. **出网依赖**：配图功能依赖第三方接口可用性，接口挂了只影响「生成」，不影响已有配图展示（`resolve` 走数据库）——这个降级设计是对的。
3. **额度告警**：建议在服务商后台设置余额告警，避免免费额度用完后静默失败（表现为一直弹「还没配置生图服务」以外的错误提示）。
4. **合规**：个人小程序涉及 AI 生成内容，正式发布时审核可能问及；保留手动触发 + 生成记录可追溯是当前最稳的姿态。

## 十、常见报错速查

| 现象 | 原因 | 处理 |
|------|------|------|
| 「生图接口返回 404」或提示模型不存在 | `IMAGE_API_MODEL` 填了 `cogview-4`，国内站已无此模型 | 改成 `glm-image` |
| 「生图接口请求超时」 | 云函数执行超时还是默认 3 秒 | 超时改 60 秒，内存改 512MB |
| 「生图接口返回 401」 | Key 填错/失效，最常见是漏了点号后那段或带了空格 | 重新复制，确认无空格无引号 |
| 「生图接口返回 429」+ 错误码 1113 | 智谱账户余额不足 | 去费用中心充值，¥5–10 够用很久 |
| 「还没配置生图服务」 | 环境变量没存上，或没重新部署 | 检查三条变量，重新「上传并部署：云端安装依赖」 |
| 图片能生成但显示不出来 | 大概率是旧版本代码在跑（$LATEST 早于 09-19 13:56） | 重新部署 dishImage |
| **调用报 `-3 / [UPSTREAM] Upstream error`，但数据库里其实有记录** | ⭐ **已定位**：调用方等待上限被突破而断开，**云函数仍在后台跑完并落库**。官方 FAQ 原文：「超时客户端会直接断开连接并报错……不允许直接调用长耗时的云函数」。生图约 30 秒，控制台「云端测试」等不了这么久 | 不是故障。改到小程序端验证，或按 P-5 做异步化 |
| 调用报 `-3`，且**数据库里没有记录、日志里也没有任何 `[dishImage]` 输出** | 容器确实没起来 | 走下方「ret=-3 二分定位」 |
| 日志里出现 `compress skipped` | 压缩依赖没装上或解图失败 | 功能不受影响（自动降级存原图），但要核对 `bytes`；确认部署时选的是「云端安装依赖」 |

### ret=-3 二分定位（已定位，此处保留为方法论）

**2026-09-26 实测结论**：`resolve`（秒回）成功、`generate`（约 30 秒）报 -3 —— 看着像"函数坏了"，实际是**长耗时函数被调用方超时断开**：`dishImages` 里留下了 `_id=番茄炒蛋` 的完整记录，`generatedAt = 22:29:27`，而报错时间是 `22:29:34`（**函数比报错早 7 秒就成功了**）。

**所以第一件事永远是先查库**，`dishImages` 里有没有那条记录？

- **有记录** ⇒ 函数成功，-3 来自调用方超时，属预期行为，**不是缺陷**（但要按 P-5 修用户体验）
- **没记录** ⇒ 才是真失败，再按下面的表二分：

| 步骤 | 操作 | 结论判读 |
|------|------|----------|
| T1 | 在同一个「云端测试」面板调**另一个**云函数（如 `menuQuery`，参数 `{}`） | 也报 -3 ⇒ **环境级问题**（欠费/停服/额度），与代码无关；正常返回 ⇒ dishImage 独有，继续 T2 |
| T2 | 调 `dishImage` 传 `{"action":"diag"}` | 看返回体 / 日志里最后一条 `[dishImage][diag]` 标记停在哪段，即可定位死点 |
| T3 | 看开发者工具**部署输出窗口**，`npm install` 那段有没有报错 | 有报错 ⇒ **依赖在云端没装上**（已做瘦身，重试一次） |
| T4 | 兜底：临时把 `package.json` 里的 4 个 `@jimp/*` 全删掉再部署 | 恢复 ⇒ 依赖问题实锤，改用零依赖方案（存原图，用 `IMAGE_API_SIZE` 向接口要小图） |
