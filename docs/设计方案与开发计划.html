01

产品定义与核心场景

一句话定义：一个只服务自己家的食谱看板。上传一张周食谱 Excel，随时知道今天和明天吃什么、每道菜怎么做、需要提前准备什么。

名称与命名落点

小程序名称 好饭。两个字，口语，问「今天吃什么好饭」时顺手就能想起来。

小程序对外名称好饭　微信平台内名称唯一，若已被占用，建议退让为「好饭 · 一周食谱」或「好饭食谱」
首页导航栏标题好饭（首页固定）
二级页导航栏标题动态：如「9月20日 周日」「莲藕消积米糊」「导入食谱」
GitHub 仓库名haofan（与小程序名同源）
云开发环境haofan-prod，日后可扩展 haofan-dev

场景 A · 早上

打开小程序看今天早餐是什么、米糊要泡什么料。需要「今天」整天的分餐次视图。

场景 B · 晚上

知道明天吃什么，并把需要解冻、腌制、泡发的东西提前处理掉。需要「明天」摘要 + 提前准备提醒。

场景 C · 做饭时

点进某道菜看配方和步骤，不用在一格长文字里翻找。需要菜谱详情页。

三条需求的功能拆解

你的需求实现方式
上传 Excel，自动对应日期生成一周食谱云函数用 SheetJS 解析矩阵表 → 人工校对页确认 → 落库为「一天一条」的文档
按天友好展示，今天与明天突出首页固定为「今天 + 明天」双卡片，今天按餐次展开，明天给摘要与提前准备；下方接本周横滑速览。必须处理今天不在任何周期内的三种状态
基于文字生成图文显示一层：菜名归一化后查 dishImages 图库精确命中；二层：按餐次配色的占位图兜底（零请求）；三层：详情页手动触发 AI 生成并缓存
明确的非目标（一期不做）：多人多家庭与账号体系、食谱在线编辑、社交分享与评论、菜谱推荐算法、分享长图海报、H5/App 版本。这些都留到二期，一期先把「导入 → 看今天」这条主链路做扎实。

表格是「矩阵式」而不是数据表

这是最重要的一个认知：列是星期，行是餐次。不是常见的「一天一行」。任何按行读的解析器都会解析失败。

        A              B        C        D        E        F        G        H
 1   9/20-9/26        周日     周一     周二     周三     周四     周五     周六   ← 表头行
 2   早 ┐             早餐主食（7 天各 1 格）                              ← A2:A3 合并
 3     ┘             早餐饮品/米糊（7 天各 1 格）                          ← A 列为空
 4   中              午餐（7 天各 1 格）

十六项结构陷阱与解析对策

类别现象解析对策
结构矩阵表，列=天、行=餐次转置：按「日期列 × 餐次行」笛卡尔展开成记录流
结构A2:A3 合并，A3 读出来是 nullA 列前向填充（forward-fill），并把空标签识别为「同餐次续行」
结构B10:H10、B11:H11 横向合并取合并区左上角值，其余列忽略，不做前向填充
结构第 9 行整行空，是分隔带整行非空数 = 0 时跳过，不产出记录
结构早餐占两行，其余餐次占一行早餐建模为两个 slot：主食 + 饮品，不假设「一餐一行」
结构A 列是桩列，混了餐次与操作说明按关键词归类：餐次词 / 备料词 / 全局备餐词，无法归类的保留原文并告警
结构G7、H7、H8 空（周末无备料说明）视为正常缺失，不告警；备料备注允许 undefined
边界表维度报 200 行 × 26 列，真实只到 H11自己扫描非空单元格求边界，禁用 max_row 之类的表维度
日期A1 是文本 9/20-9/26，无年份正则提取 M/D，补年份；用表头星期名反推校验，跨年时 end 年 +1
日期表头是「周日 → 周六」，周日打头列序映射必须按 B=周日，不能默认 B=周一；建议用常量表而非取模
文本菜名与配方混在一格，分隔符不统一按 ： ； 换行 三级切分，取第一个命中的位置切；未命中则整格即菜名
文本/ 表示「二选一」而非并列拆成 options[]，展示为「A 或 B」，不产生两条并列菜品
文本同格内序号分隔符混用 4. 4， 3，步骤拆行用正则 ^\s*\d+\s*[.、,，)）] 统一识别，而不是按固定符号切
文本单位混写：克/g/ml/毫升/个/颗/片/1.5只做展示层归一化，不影响匹配；胡萝卜1.5 这类无量词值原样保留
文本全角半角混用、双空格、尾部多余顿号切分前统一规范化：折叠连续空白、去尾部标点、括号统一
资源表内没有任何图片对象配图素材必须另建，见第 07 节的三层方案
一个必须提前处理的时间问题：这份表的周期是 2026-09-20 至 09-26，而今天是 09-18（周五）。也就是说，你上传的这份表里，今天和明天都没有数据。首页如果只做「有数据」一种形态，第一次跑起来就是一片空白 —— 这是第 06 节要把首页设计成三态的直接原因。
03

技术选型与总体架构

微信原生 + 云开发，解析全部下沉到云函数

层选择理由
前端框架微信小程序原生（TypeScript 模板）与云开发深度集成，没有额外构建链；TS 能拿到完整的 openapi 类型提示，单人开发时少踩 API 拼写的坑
UI 组件TDesign 小程序版腾讯系，组件覆盖全（Cell / Collapse / Toast / Skeleton / Dialog 都够用），省掉自研交互组件的时间。若想完全掌控样式，也可只用 3–4 个自研组件，不影响架构
Excel 解析云函数 + SheetJS（xlsx）关键决策：小程序主包只有 2MB，放不下 xlsx 库；云函数是完整 Node 环境，解析完直接返回结构化 JSON，一次往返
数据存储云开发数据库免运维、免服务器、免备案、免 HTTPS 域名。默认「仅创建者可读写」权限天然满足单用户场景
文件存储云开发云存储图片与原始 Excel 全部走云存储，小程序包体只放图标
日期处理dayjs（小程序端 + 云函数）体积小，ISO 周、加减天、跨月处理都成熟，避免手写 Date 运算出错
版本控制GitHub + GitHub Actions解析器单元测试跑在 CI 上，这是唯一有真实回归风险的部分

云函数职责划分

云函数职责设计要点
menuParse读云存储中的 xlsx → 返回结构化 JSON + 告警列表。不写库纯函数式，便于单测；输出直接喂给校对页
menuSave接收校对后的 JSON → 写 periods 与 days按 _id 幂等 upsert，重复导入同一周即覆盖，不堆垃圾
menuQuery按日期查单天、按周期查整周、查今天与明天「今天」和「明天」分两次独立查询，因为跨周时它们可能属于不同周期
dishImage菜名 → 图片：命中查询、生成、写缓存生成能力默认关闭，由前端显式触发
为什么解析要分「解析」和「保存」两个云函数？因为这张表的脏数据程度决定了自动解析不可能 100% 准确。menuParse 只负责「尽力解析并如实报告问题」，把结果交给人在手机上校对一次；确认无误后再由 menuSave 落库。这样解析器可以放心地容错，而不必为了自动化去做过度猜测。

菜名归一化函数是配图体系的地基，两端要共用同一份实现（放在 shared/normalize.ts，小程序端与云函数各引用一份编译产物）： 
function normalizeDishKey(name) {
  return String(name)
    .replace(/[\s\u3000]+/g, "")     // 去所有空白（含全角空格）
    .replace(/^\d+\s*[.、,，)）]/, "") // 去开头序号
    .replace(/[，、;；。,.]+$/, "")   // 去尾部标点
    .replace(/[（(][^）)]*[)）]/g, "") // 去括号备注
    .replace(/[＋+]/g, "")            // 去加号
    .trim();
}
05

解析层详细设计

整个项目风险最高的部分，也是应该最先写、最先测的部分

十步解析算法

1

读表

SheetJS 以 header:1, defval:null, raw:false 读出二维数组。按字符串读，避免日期序列号把文本日期吃掉。

2

自扫边界

遍历二维数组求非空单元格的 min/max 行列。不使用表维度 —— 这份表会报 200 行，直接扫会产出巨型空表。

3

定位表头行

在边界内逐行扫描，找到第一行含有 ≥5 个匹配 /^周[一二三四五六日天]$/ 的单元格的行。记下这些单元格的列号与星期值，得到「日期列映射」。

4

解析周区间

从表头行左侧取 9/20-9/26，正则 (\d{1,2})\/(\d{1,2})\s*[-~至]\s*(\d{1,2})\/(\d{1,2}) 提取。补年份：默认当前年；若推算出的起始日星期与表头首列星期不符，则试 ±1 年。若结束月 < 开始月，结束年 +1（跨年周）。

5

生成日期序列

用 dayjs 从起始日推进 7 天，与日期列一一对应。用每个日期的实际星期名与表头文字做逐列校验，不符则发 W003。

6

A 列前向填充

向下遍历表头行之后的行，A 列为空时沿用上一个非空值。这一步解决 A2:A3 合并；同时记录「本行 A 列是否为空」，空的即为同餐次续行。

7

行归类

按 A 列标签把行分成四类：餐次行（早/中/加餐/晚）、备料行（含「食材处理」「解冻」「备料」）、全局备餐行（「食材准备」「备餐」）、分隔行（整行空）。无法归类的行保留原文并发 W010。

8

转置展开

对每个日期列 × 每个餐次行取单元格，产出一条 meal 记录；对备料行取文本归入 prepNotes；对全局备餐的合并单元格只取左上角值。

9

菜名切分

先规范化文本，再找第一个 ： / ； / 换行 的位置切分。切分前处理后得到 dishName，切分后得到 recipe。命中 / 时拆成 options。

10

产出与告警

输出 { period, days[], warnings[] }。days 覆盖全部 7 天（含空天），空缺项标 missing，不跳过 —— 首页三态需要知道「这一天存在但没内容」和「这一天不在周期内」的区别。

菜名切分的核心实现

const SPLITTERS = ["：", ":", "；", ";", "\n"];

function splitDish(cellText) {
  if (!cellText || !cellText.trim()) {
    return { displayTitle: "", options: [], recipe: null, needsReview: false };
  }

  // 1) 规范化：折叠空白、去尾部标点，但保留换行用于步骤拆分
  let text = String(cellText)
    .replace(/[\u3000]/g, " ")
    .replace(/[ \t]{2,}/g, " ")
    .trim();

  // 2) 找第一个分隔符的位置
  let cut = -1;
  for (const s of SPLITTERS) {
    const i = text.indexOf(s);
    if (i >= 0 && (cut < 0 || i < cut)) cut = i;
  }

  let namePart = cut >= 0 ? text.slice(0, cut) : text;
  let recipe   = cut >= 0 ? text.slice(cut + 1).trim() : null;

  // 3) 清掉菜名里的序号与尾部标点
  namePart = namePart
    .replace(/^\s*\d+\s*[.、,，)）]\s*/, "")
    .replace(/[，、;；。,.]+$/, "")
    .trim();

  // 4) 二选一："/" 拆成 options，不产生并列菜品
  const options = namePart.split("/").map(s => s.trim()).filter(Boolean);

  const displayTitle = options.length > 1
    ? options.join(" 或 ")
    : (options[0] || namePart);

  // 5) 可疑项标记：切分后菜名仍然过长，说明分隔符没命中
  const needsReview = displayTitle.length > 20 || options.some(o => o.length > 16);

  return { displayTitle, options: options.length > 1 ? options : [], recipe, needsReview };
}

告警码表

码级别触发条件处理
W001阻断找不到表头行（无 ≥5 个星期单元格）中止导入，提示「表格模板不匹配」并展示期望格式
W002警告年份是推断值（本表必然触发）校对页顶部显示年份选择器，默认推断值，需用户确认
W003警告表头星期名与日期推算的星期不一致逐列列出冲突，让用户选以哪个为准
W004提示检测到合并单元格并已自动填充展示填充前后对照，可回退
W005警告某天某餐次为空在校对页标注空缺，允许留空保存
W006警告菜名切分可疑（长度超阈值）高亮该行，附原文，允许手动改菜名与配方
W007提示单元格含 /，已按二选一处理展示拆分结果，可切回「并列两道菜」
W008警告与已有周期日期重叠让用户选「覆盖 / 跳过 / 并存」

首页三态逻辑（体验核心）

首页渲染前先判断今天落在哪个状态。今天与明天要分别查询，因为周日晚上「明天」已经属于下一个周期了。

function resolveDayState(dateStr, periods) {
  const p = periods.find(p => p.startDate <= dateStr && dateStr <= p.endDate);
  if (p) return { state: "in-period", period: p };

  const next = periods
    .filter(p => p.startDate > dateStr)
    .sort((a, b) => a.startDate.localeCompare(b.startDate))[0];

  if (next) {
    return { state: "before-period", period: next, gapDays: diffDays(dateStr, next.startDate) };
  }
  return { state: "after-period" };
}
状态触发条件首页呈现
in-period今天落在某个周期内今天卡片按餐次逐行展开（早 / 早餐饮品 / 中 / 加餐 / 晚），每行左侧配图缩略图；明天卡片折叠为摘要行 + 提前准备提示条
before-period今天在已有周期之前（你当前就是这种）显示「N 天后开始新一周食谱」的大数字倒计时 + 该周第一天预览 + 可点进完整周视图
after-period今天晚于所有周期空态卡片「上一周食谱已结束」+ 周期区间 + 「去导入新一周」主按钮
「提前准备」提示条的设计：你的表格里第 7 行「食材处理（早）」、第 8 行「解冻洗净备用（晚）」和「备餐」行，本质是前置准备信息，散落在表格底部很容易被忽略。首页把它们提炼成明天卡片下方的一条橙色提示，例如「提前准备：牛肉腌制 · 鳕鱼去腥」。这是这个产品相对「直接看 Excel」最明显的增量价值。

为什么把 AI 生成做成手动触发

  • 成本可控。一周 35 道菜，如果导入即全部生成，一次导入就是 35 次调用。手动触发后，只有你真的想看的那几道菜会被生成。

  • 效果更好。自动生成的图你多半不会看，手动点的那些才是你真关心的菜，值得花时间调提示词。

云数据库建 periods / days / dishImages 三个集合，权限保持默认「仅创建者可读写」；四个云函数在开发者工具里右键「上传并部署：云端安装依赖」；AI 生图的 API Key 写入云函数环境变量，不入代码库。

3

建立发布通路

两条路并行：日常自用走体验版 —— 开发者工具上传 → 版本管理里设为体验版 → 手机扫码即用，家人拉进体验成员名单即可，不等审核；对外正式版走「提交审核 → 通过后发布」，审核一般 1–2 天。

两条通路怎么选：只给自己家，体验版就够 —— 每次改完代码上传并设为体验版，扫码即用。只有当你想让家人能直接在微信里搜到、或用到需要正式版权限的接口时才走审核。注意一个联动规则：一旦正式发布，免费体验环境会在上线后第 15 天到期，届时需转付费套餐。

唯一真正会咬人的运维风险：套餐到期 → 数据清除。到期前 7 天开始公众号隔天通知，到期次日起 7 天内可续费找回，第 8 天系统释放资源，数据不可恢复。对策有三层：腾讯云账户预充值 + 开自动续费（注意自动续费只支持腾讯云支付，需从微信支付切换）；「我的」页加一个 dishImages 一键导出，每月点一次；periods 与 days 本来就能从源 Excel 幂等重建。
这个项目有一块天然的安全垫：Excel 本身就是全量备份。periods 与 days 的主键设计成日期幂等，就是为了「数据库丢了 → 把源表格重新导入一遍」这条恢复路径。真正不可再生、值得单独备份的只有 dishImages（图片文件 + 菜名映射）。所以灾难恢复的完整动作 = 重导 Excel + 恢复一份 JSON + 图片文件还在云存储（或另存一份），十分钟以内。
